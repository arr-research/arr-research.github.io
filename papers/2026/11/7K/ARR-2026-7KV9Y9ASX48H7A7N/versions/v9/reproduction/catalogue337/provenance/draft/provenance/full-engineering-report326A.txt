3. Quiescence and grant exclusion: lines 50–61.
service_stop_attempted is set before calling systemctl stop. On the normal path, the script checks inactive and MainPID=0 after stop, rechecks the physical paths and then obtains a SQLite BEGIN IMMEDIATE write reservation. It reads the catalogue after the reservation and requires exact PREVIOUS object equality, including version/hash/author. The SQL count covers all historical-revision grants joined to an agent grant with state approved, uses=0 and future expiry, not merely this PID; any counted row aborts. This avoids silently consuming or deleting unused grants. A missing table/query failure aborts. No SQL INSERT, UPDATE or DELETE is in the helper. The reservation is held through the replacement and final readback. Its protection covers cooperative SQLite writers, not arbitrary direct catalogue writers or unsupervised alternative issuers. See F3/F4.

4. Backup and unrelated entries: lines 21–25 and 62–66.
The backup is exclusively created with mode 0600, flushed, fsynced, its parent directory synced, and raw bytes/owner/mode read back. Failure precedes mutation of the catalogue. The only in-memory assignment changes data[PID]. The script compares every other parsed entry and the number of entries before serializing. It re-reads the original catalogue immediately before creating the replacement temp and rejects a detected intervening byte change. Preservation is semantic for all unrelated JSON values, not byte preservation of their whitespace or key ordering; the whole object is reserialized. The exact original bytes remain in the backup. This is consistent with a single-entry catalogue update, subject to trusted valid JSON and no external writers.

5. Atomic replacement and durability: lines 67–76.
The temp is a sibling of the catalogue, exclusively created and initially private, written/flushed/fsynced and read back. It receives the original POSIX mode and owner/group, is fsynced again, and is atomically renamed onto the catalogue with os.replace on the same directory/filesystem. The parent directory is synced after rename. The final bytes and uid/gid/mode are compared with the intended values before db.commit and success fields. These are appropriate normal-path controls for an atomic file replacement. The SQLite transaction does not make the JSON rename transactional; there is no SQL data write to roll back the file. Existing ACLs, extended attributes, security labels and hard-link relationships are not preserved or checked by this code. No new326 regression was introduced here.

6. Failures, restart and retained result: lines 77–95.
Main-body exceptions are recorded with traceback and FAILED_PRESERVED, followed by a restart attempt if a stop was attempted. A restart error is caught and gives a failed result; the final exit is nonzero if error is set. Successful exit requires replacement and restarted status. The recovery message correctly says that SQL rollback cannot undo a rename and that the actual catalogue and backup require inspection before any further mutation. The restart and result-retention paths are not fully exception-contained: db.close and the final catalogue hash read lie outside their own protective try blocks. These inherited issues are explained below; predecessor success is not a proof that the failure paths work. INHERITED FINDINGS AND BOUNDARIES

F1 — P2, concrete cleanup/reporting fault-containment gap, unchanged from320.
Locations: line 80 and line 87.
If db.close() raises while unwinding the main operation, execution leaves this finally block before the systemctl start at line 83 and before OUT is written. Independently, P.is_file()/P.read_bytes() at line 87 can raise after a restart, bypassing finished_at, OUT and the final print. For example, a read error encountered at the main final-readback step can recur in line 87 and suppress the structured failure report. The process would fail, but complete result retention would not be guaranteed. The initial attempt log and earlier backup may remain; they must not be mistaken for a terminal result. This is a static control-flow finding, not an observed host failure. A later hardening revision should isolate cleanup and actual-byte observation failures so restart is independently attempted and an OUT failure record can still be emitted. Do not change the currently frozen source during this audit.

F2 — P2 operational recovery boundary, intentionally inherited; not a new parameter defect.
Locations: lines 72–89.
After os.replace succeeds, subsequent fsync/readback/commit/result errors can leave the new catalogue installed. FAILED_PRESERVED does not mean the catalogue was unchanged or rolled back. The finally block attempts to restart even after post-rename verification failed, so the service is not guaranteed to remain quiescent until an operator resolves that failure. This is consistent with the source's explicit no-automatic-rollback message, but it is not an all-fault fail-closed deployment transaction. An actual nonzero outcome requires inspection of actual bytes, preserved backup, service status and native context before further mutation. If policy requires keeping service down after failed final validation, this exact source does not implement that policy. No such new guarantee should be inferred from the PR's use of 'guarded'.

F3 — P2 preflight assumptions not verified here, inherited.
Locations: physical() lines 26–30, source/config checks 38–43, quiescence 52–57, pre-rename check66 and rename72.
physical() rejects unsafe parent modes and symlinks but does not require P/DB themselves to be owned by a particular account or disallow their group/world write bits. It checks no ACL, hard-link count or trusted owner for each ancestor. The service is stopped, but there is no filesystem lock against an unrelated writer, no mask against an external service start, and no atomic compare-and-swap between line66 and line72. The SQLite reservation cannot prevent direct JSON writes. These are acceptable only under a protected-host/no-out-of-band-writer assumption established by native-context inspection. The present source review did not inspect the host or prove those assumptions. The same assumptions existed in320.
